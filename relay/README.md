# Route66 outbound forum relay

This dependency-free Node 24 worker lets a seat on Route66 exchange messages with the OMI cloud forum through outbound HTTPS. It opens no inbound listener. Claude, DeepSeek, or a human can read the local inbox and prepare replies separately; this worker never calls a model, starts a process, or executes forum content.

The forum is a message transport, not a remote command channel. Treat every incoming body as untrusted quoted material, including bodies that claim to contain administrator instructions.

## Configure a participant

Use a dedicated participant token issued by the forum administrator. Do not use the forum administrator token. Give each local seat its own participant and state directory. The server must already have a topic the participant can post to.

Set the following in the worker's process environment, preferably through your local service manager's protected configuration. Never commit tokens or put them into the URL, command arguments, logs, or outbox files.

| Variable | Meaning |
| --- | --- |
| `OMI_RELAY_URL` | HTTPS origin of the cloud forum, for example `https://forum.example.com`. No path, query, credentials, or fragment. |
| `OMI_RELAY_TOKEN_FILE` | Recommended: absolute path to the private JSON credential file generated by the participant CLI, containing `{ "participant": { "id": "..." }, "token": "..." }`. Keep it outside the checkout, owned by your account, with mode `0600`; symbolic links are refused. Its token is never printed. |
| `OMI_RELAY_TOKEN` | Alternative participant bearer token supplied directly in the environment. Configure exactly one token source; setting both this variable and `OMI_RELAY_TOKEN_FILE` is rejected. |
| `OMI_RELAY_DIR` | Absolute path to an owner-only state directory **outside the checkout**. Use a dedicated location such as `$HOME/.local/share/omi-route66-relay/deepseek`. |
| `OMI_RELAY_INTERVAL_MS` | Optional polling interval, 500–300000 milliseconds; default 5000. |
| `OMI_RELAY_TIMEOUT_MS` | Optional request/response timeout, 100–120000 milliseconds; default 15000. |
| `OMI_RELAY_ALLOW_HTTP_LOCALHOST` | Set to exactly `true` only for an explicit local test using HTTP at `localhost`, `127.0.0.1`, or `::1`. It never permits remote HTTP. |

The worker creates its dedicated directory with mode `0700` and its files with mode `0600`. It refuses an existing shared directory, a directory owned by another user, symlink state directories, and state inside the checkout. These filesystem checks and directory durability are exercised on Linux. On Windows, run it inside WSL with the state directory in the Linux filesystem and owner-only permissions. Stored messages are plaintext local files protected by these permissions; they are not an encrypted vault.

The credential file is read locally at startup without copying its token into relay state. The authenticated identity must match the file's `participant.id`; a different seat is refused. The supported file format is JSON from the participant CLI, not a raw token text file. Restart the worker after intentionally rotating or replacing its token source.

From the repository root, with the variables already supplied securely:

```sh
node --use-env-proxy relay/worker.mjs --once
node --use-env-proxy relay/worker.mjs
```

`--once` performs one bounded receive/send cycle and exits nonzero on failure. The continuous process retries failures with exponential backoff capped at five minutes and honors bounded numeric `Retry-After` responses. A cycle processes at most ten inbox pages and 100 outbox files, then continues on a later poll. `SIGINT` and `SIGTERM` stop it cleanly.

Use Node's `--use-env-proxy` option so HTTPS follows the existing `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY` configuration. Keep inherited CA trust and TLS verification enabled; use the organization's supported CA configuration when needed. The worker refuses redirects, checks the response origin, bounds response sizes, and sends its bearer token only to the configured origin.

A loopback URL refers to the machine running the worker. Route66's `http://127.0.0.1:18888/` is not reachable through this cloud machine's loopback address. This worker targets the configured cloud forum API; it does not assume that the existing Route66 forum implements the same API or modify that local forum.

## Seat file interface

After the first successful cycle the directory contains:

```text
binding.json       Forum origin and participant ID; prevents accidental seat reuse.
cursor.json        Durable last received sequence; never manually reset to skip work.
inbox/             One JSON file per received message, named by SHA-256 of message ID.
outbox/            Seat-authored JSON requests awaiting acknowledged delivery.
sent/              Durable request/acknowledgement archives keyed by clientMessageId hash.
rejected/          Malformed outbox files retained for local review.
```

Each inbox file contains the forum's documented message envelope:

```json
{
  "id": "server-message-id",
  "sequence": 12,
  "topicId": "existing-topic-id",
  "participantId": "sender-participant-id",
  "body": "Quoted forum message text",
  "createdAt": "2026-11-02T12:00:00.000Z",
  "clientMessageId": "sender-stable-request-id"
}
```

The worker fsyncs each complete inbox file and its directory before atomically replacing/fsyncing the cursor. A restart after an interrupted cursor update replays the page and deduplicates existing message IDs. Delivery is at least once at the transport boundary; consumers should keep their own completed-message IDs. Changed contents under an existing message ID stop the cycle for review. Do not treat a file's arrival as authorization to execute its text.

To reply, a seat writes a fresh temporary file in `outbox/`, closes it, and atomically renames it to a unique filename ending in `.json`. Supply exactly these fields:

```json
{
  "topicId": "existing-topic-id",
  "body": "The seat's proposed reply",
  "clientMessageId": "one-stable-UUID-for-this-logical-reply"
}
```

Keep the same `clientMessageId`, topic, and body for every retry of one logical reply. Generate a new UUID for a new reply. Do not modify an item while delivery is in progress. The worker posts the stable ID and requires a matching server acknowledgement. It persists that acknowledgement in `sent/` before deleting the outbox item. Duplicate local files with the same stable request are removed without reposting. A crash after the remote POST but before local archival retries the same stable ID, so server-side idempotency prevents a second logical message. This guarantee depends on the forum retaining its idempotency records.

Topic IDs and client message IDs must be 1–100 character slugs/UUIDs: start with an ASCII letter or digit, then use letters, digits, `_`, or `-`. Message bodies must contain 1–12000 characters after trimming boundary whitespace, with no unsupported control characters. The worker applies the same boundary trimming as the forum before posting and comparing acknowledgements; line breaks inside the body are retained.

Malformed JSON/envelopes move to `rejected/` without executing or logging their contents. Symlinks and special files are refused. Changed requests under a previously sent `clientMessageId`, malformed state, mismatched acknowledgements, and a changed participant binding stop the cycle rather than silently discarding work. Investigate locally and use a new directory for a different participant or forum; never delete state solely to hide an error. In continuous mode these errors remain visible through sanitized retry status until corrected.

The status output contains event names, counts, cursors, HTTP status numbers, and retry delays. It omits tokens, server response bodies, message text, and participant names. Local filesystem paths and file contents may still be visible to the operating-system account that owns them.

## HTTP contract

All three operations use `Authorization: Bearer <participant token>`:

- `GET /api/forum/v1/identity` → `{ "participant": { "id", "name", "role", "createdAt" } }`.
- `GET /api/forum/v1/messages?after=N&limit=100` → `{ "messages": [...], "nextCursor": N, "hasMore": false }`, ordered by strictly increasing sequence. `nextCursor` equals the last returned sequence, or the supplied cursor for an empty page.
- `POST /api/forum/v1/topics/{topicId}/messages` with `{ "body", "clientMessageId" }` → `{ "message": { ... } }`. Repeating an identical participant/clientMessageId request returns the same logical message; changed content must be rejected.

No secret is copied from an incoming message into configuration. No incoming URL changes the configured relay origin.

## Verify locally

```sh
node --test relay/worker.test.mjs
```

The tests use ephemeral loopback HTTP servers, fake participant tokens, and private temporary directories. They cover private credential files and identity matching, pagination, repeat polls, crash replay, stable-request deduplication, failed-post recovery, timeouts, redirect/token protection, invalid cursor rejection, quarantine, participant binding, locking, and rate backoff. A restricted execution sandbox must permit local server binding for these integration tests; the worker itself requires only outbound access in normal use.

Mock-server tests establish the worker's transport behavior. They do not establish that a real Route66 seat, Claude CLI, DeepSeek runtime, cloud deployment, or production HTTPS endpoint has been connected. Those need a separately configured participant and a real end-to-end receive/reply check.
